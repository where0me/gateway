# Zigbee 工业网关当前代码功能与合并说明

> 文档用途：供后续开发人员了解当前代码已经实现的能力、三端协作方式、数据协议、数据库结构、合并范围及验证方法。  
> 代码快照日期：2026-09-01  
> 涉及工程：Linux/RK3506 网关、React 前端、TI CC1352R1 协调器、STM32WB55 终端节点。

## 1. 系统定位

当前系统是一套面向工业状态监测的 Zigbee 边缘网关。系统负责节点入网管理、在线监测策略下发、手动或周期采集、传感器数据接收、振动原始波形可靠传输、SQLite 本地存储以及网页展示。

系统由四部分组成：

1. **STM32WB55 终端节点**：采集温度、磁场、数字麦克风、模拟麦克风和三轴振动；执行自动监测周期；把振动原始值暂存在外部 QSPI Flash；通过 Zigbee 上报数据。
2. **CC1352R1 Zigbee 协调器**：维护 Zigbee 网络；在终端 Zigbee 私有命令与 Linux 串口协议之间进行转发；上报命令入队和无线投递结果。
3. **Linux/RK3506 网关后端**：管理设备白名单和扫描流程；通过串口控制协调器；接收、校验、解压和保存数据；提供 HTTP/WebSocket 接口。
4. **React 前端**：提供状态总览、节点管理、系统设置、在线监测控制、采集结果、振动特征和波形展示。

整体数据路径如下：

```text
浏览器
  │ HTTP / WebSocket
  ▼
gateway-server ── SQLite gateway.db
  │ FE/CMD/LEN/PAYLOAD/BCC 串口帧
  ▼
CC1352R1 协调器
  │ Zigbee 0x0402 集群私有命令
  ▼
STM32WB55 终端 ── 外部 QSPI NOR Flash
```

## 4. 设备扫描、入网和白名单管理

### 4.1 扫描流程

1. 前端调用 `POST /api/device/scan`。
2. 网关通过串口向协调器发送 `0x03`，协调器开放 Zigbee PermitJoin。
3. 新终端入网后，协调器上报 `0x84`，内容包括终端 MAC 和网络短地址。
4. 网关把节点放入待确认队列，并按节流规则发送 `0x04` 查询节点名称、型号和信号强度。
5. 协调器返回 `0x85` 节点信息，前端节点管理页显示扫描结果。
6. 用户确认添加后，网关把设备写入 `devices` 白名单。新节点固定开启周期监测，并在入网后的 30 秒接收窗口中通过 `0x99` 主动查询当前采样配置。
7. 停止扫描时，网关发送 `0x05` 关闭 PermitJoin，并清理未确认节点。

### 4.2 已授权设备重连

网关收到入网通知后首先按 MAC 查询 SQLite：

- MAC 已存在：更新短地址和在线状态并重新查询设备身份；终端在恢复或重连后的 30 秒窗口内主动查询最新采样参数。
- MAC 不存在且当前正在扫描：进入待确认列表。
- MAC 不存在且未开放扫描：立即向协调器下发踢出指令。

这种设计使短地址变化不会影响设备身份；数据库和前端始终以 64 位 MAC 为主键。

### 4.3 彻底移除

前端调用 `POST /api/device/remove` 后：

1. SQLite 在同一事务中写入独立的 `revoked_nodes` 撤销保护记录，并删除该 MAC 的业务数据和 `devices` 记录。
2. 网关向协调器发送 `0x02` 踢出目标 MAC；节点休眠或漏收时，后端在它下一次上行时按 3 秒节流重试。
3. 网关删除该设备尚未完成的 V1/V2 内存组包状态，防止迟到数据重新入库。
4. 协调器向终端发出带 `rejoin=0` 的离网操作。
5. 终端停止采集和上传，作废待传振动批次，擦除内部 Flash 中的 Zigbee 网络记录，并自动重新扫描 11～26 信道；只有协调器开放入网时才能重新作为待确认节点出现。
6. 协调器的本地 `NLME-LEAVE.confirm` 不作为节点已擦除NVM的证据；只有 Leave indication 后才清理密钥/旧子节点关系。后端仍将记录转为 `guard` 长期保留，再次看到旧节点时重新下发离网命令。

只有用户再次确认该 MAC 入库时才删除 `revoked_nodes` 记录并恢复业务权限。短地址被协议栈重新分配给其他 MAC 时，后端会解除旧撤销记录的短地址绑定，避免误踢新节点。

## 5. 周期在线监测和节点主动取参

### 5.1 工作方式

- 查询或保存全局策略：`GET/POST /api/monitor/settings`。

正式入库节点始终开启周期监测。前端不再提供监测开关和立即采集按钮；保存策略时只写入网关数据库，不主动唤醒节点。

终端在首次入网、持久化恢复或掉线重连后开启 30 秒快速接收窗口，并发送 `0x99` 查询。之后每个采集周期开始前先开启 5 秒快速接收窗口并发送 `0x99`，只有收到网关用 `0x0C` 返回的最新参数和授权后才开始采集；查询超时则跳过本轮。采集和计算可并行，但无线结果固定按“上传状态、温度、磁场、数字麦克风、模拟麦克风、振动数据、完成状态”的顺序发送，完成后额外保持 5 秒快速接收。

删除设备后，后端会保留一条待移除记录。睡眠节点再次上行时，后端会重试离网命令；其中采集前的 `0x99` 查询由短地址直接拦截，不下发 `0x0C`，从而在传感器采集和批量上传开始前完成阻断。其余上行触发的重试按 3 秒节流，避免振动分片造成命令风暴。

节点在线状态同时使用两类依据：收到协调器明确离网事件时立即离线；突然断电没有离网报文时，以节点最近一次实际获取的采集周期为准，连续两个采集周期再加 30 秒仍无任何有效上行则判定离线。`0x99` 和后续传感器报文都会刷新活跃时间，不额外增加无线保活包。后端为每台节点保存最近一次成功下发的采集周期，避免修改全局策略后、尚未唤醒获取新参数的节点被提前判离线。

协调器仍可返回：

- `0x8E`：协调器已接受命令并放入 Zigbee 发送队列；不代表节点已经执行。
- `0x90`：AF/APS 无线投递结果；表示协调器到终端的无线传输结果，仍不等价于业务执行完成。
- `0x8D`：终端实际工作状态；这是前端判断采集进度的业务状态。

### 5.2 采样策略参数

| 参数 | 数据库默认值 | 网关允许值/范围 | 终端用途 |
| --- | ---: | --- | --- |
| 自动采集周期 | 1800 s | 60～86400 s | 固定周期监测的采集间隔 |
| 振动采样率 | 26667 Hz | 固定 26667 Hz | IIS3DWB实际输出采样率 |
| 振动采集窗口 | 1000 ms | 500/1000/1500 ms | 决定本批振动点数和Flash占用 |
| 数字麦克风采样率 | 46875 Hz | 固定 46875 Hz | 当前时钟配置下SAI实际帧率 |
| 数字麦克风窗口 | 1000 ms | 500/1000/1500 ms | 数字声级独立计算窗口 |
| 模拟麦克风采样率 | 256000 Hz | 固定 256000 Hz | TIM2触发ADC的实际采样率 |
| 模拟麦克风窗口 | 1000 ms | 500/1000/1500 ms | 模拟声级独立计算窗口 |

采样策略保存在网关 `monitor_config` 单行表中。`poll_interval_sec` 字段只为兼容旧数据库和旧协议布局保留，不再驱动 5 秒父节点轮询。终端收到配置后更新 RAM 中的 `APP_ZIGBEE_MonitorConfig_t` 并重新安排下一次采集。终端不单独持久化业务参数，恢复网络后会主动查询网关。

### 5.3 终端采集状态机

| 状态值 | 名称 | 含义 |
| ---: | --- | --- |
| `0x00` | sleep | 旧协议兼容状态，正常流程不再使用 |
| `0x01` | waiting | 等待下一次周期采集 |
| `0x02` | capturing | 正在采集传感器数据 |
| `0x03` | uploading | 采集完成，正在上传振动数据 |
| `0x04` | complete | 本批数据校验并上传完成 |
| `0x05` | error | 采集、Flash 或上传发生错误 |

状态上报携带 `monitoring_enabled` 和 32 位批次 ID，网关更新设备影子并通过 WebSocket 推送给前端。代码保持 `uploading` 状态直到当前批次收到网关最终确认，避免采集结束到上传启动之间短暂显示为等待或睡眠。

### 5.4 定时与低功耗

- 自动采集计时器运行在终端，不在 Linux 网关。
- RTC Timer Server 回调只累加采集时间并唤醒 `UTIL_SEQ` 任务；Zigbee 操作和定时器重装在任务上下文执行，不在中断上下文直接处理。
- 终端不再固定周期轮询父节点；入网/恢复后快速轮询30秒，每轮采集前快速轮询5秒完成授权取参，整批上传完成后再快速轮询5秒。
- 无采集任务时进入 CPU SLEEP 等待。当前实现是 CPU 低功耗等待，不应表述为整个设备完全断电。
- 自动周期从新一轮采集开始重新计时；振动上传由独立任务继续执行，不把长时间上传直接串行阻塞到下一周期。

### 5.5 Zigbee信道策略

- 后端每次启动都把数据库策略重置为 `auto`，清空手动目标信道；手动策略只在本次后端运行期间有效。
- 协调器有有效持久化网络时直接恢复原PAN ID、密钥和实际信道，不执行自动扫描；恢复后的策略仍显示为自动。
- 没有持久化网络或恢复失败时，协调器使用11～26全信道掩码自动扫描并新建网络。
- 协调器通过 `0x9A` 上报“无持久化数据/恢复成功/恢复失败”；`0x8A` 同时携带启动来源和最近恢复结果，避免Linux后端启动较慢时错过一次性报文。
- 手动选择11～26信道。空网络由协调器切换；已有节点时先向睡眠节点单播标准 `Mgmt_NWK_Update`，再广播更新，协调器延时切换自身信道。
- 仍有节点采集或上传时拒绝迁移。正常迁移不改变短地址；异常重入网可能改变短地址，因此数据库始终以MAC为设备主标识。
- `zigbee_config` 分别保存会话策略、实际PAN ID、实际信道和启动来源；恢复得到的信道不会被误记为手动目标信道。

## 6. 传感器采集与同批数据关联

每次开始采集时，终端生成一个 32 位批次 ID。当前格式为：

```text
高16位：本次开机随机 nonce
低16位：本次开机内从 1 递增的采集计数
```

这样可以降低终端复位后批次 ID 与旧数据冲突的概率。前端默认只显示低 16 位作为较友好的“采集批次”，完整 ID 保留在字段和提示中。需要注意：低 16 位展示序号不是跨断电永久递增的全局序列。

同一轮的温度、磁场、数字声级、模拟声级、振动特征和振动原始值均携带同一个完整批次 ID。网关通过 `(mac, batch_id)` 关联，前端查询某个振动批次时只显示该批次对应的其他传感器值，不用另一批最新值补位。

### 6.1 温度

- 终端通过 I2C 读取实际温度。
- Zigbee 载荷使用 0.01 ℃ 的有符号整数。
- 网关写入设备最新值、`temperature_data` 历史表和 `collection_values` 同批表。

### 6.2 磁场

- 终端读取 X/Y/Z 三轴原始磁场并换算为 μT。
- 网关保存最新值、磁场历史和同批数据。
- 前端按 X、Y、Z 三列展示。

### 6.3 数字与模拟麦克风

- 两路麦克风按配置的采样率和窗口计算声级。
- 数字麦克风使用 `0x88`，模拟麦克风使用 `0x89`。
- 网关分别保存最新值、历史值以及同批记录。
- 模拟声级仍使用临时校准参考，前端明确标注为估算/待校准。

### 6.4 振动特征

终端基于完整采样窗口计算每个轴的：

1. RMS；
2. 峰值；
3. 峰峰值；
4. 峭度；
5. 主频估计。

特征以 `×1000` 的 `int32` 形式传输，网关除以 1000 后展示。当前主频实现基于去均值后的正向过零计数，不是 FFT 频谱峰值；合并代码时不要误改文案为 FFT 主频。

## 7. 振动原始数据 V2 可靠传输

### 7.1 设计目标

旧实现对 26667 个三轴点逐包发送，包数多且近似逐包等待确认，一批可能耗时数分钟。V2 实现的目标是：

- 保留完整的一秒三轴 `int16` 原始值；
- 不在 MCU RAM 中保存整批 160002 字节；
- 使用无损压缩降低 Zigbee 包数量；
- 窗口内连续发送，不逐个等待 ZCL 默认响应；
- 通过网关缺包位图只补缺失分片；
- 断电、网关重启或暂时失败后可以恢复；
- SQLite 成功提交后才允许终端释放 Flash。

### 7.2 外部 Flash 多槽保存

- 每个槽占60个4 KiB扇区，共245760字节。
- 第一个扇区保存批次、采样率、点数、原始 CRC、三轴特征、内部顺序号、头 CRC 和确认标志。
- 后续空间保存最多40001 × 3 × 2 = 240006字节原始数据。
- 槽数按Flash实际容量计算，代码最多使用16槽；1 MiB Flash可使用4槽。
- 元数据最后写提交标记。断电导致的半写批次不会被当成可上传数据。
- 未收到网关最终确认的槽不能覆盖；Flash 满时跳过新采集并明确报错。
- 上传已确认槽可以复用；坏头槽被隔离，不自动擦除可能可恢复的数据。
- 终端复位后扫描槽并按内部保存顺序继续上传。
- 可迁移校验有效的旧版单槽振动记录。

### 7.3 分块压缩

- 每 512 个 XYZ 点作为一个独立窗口，最后一个窗口可不足 512 点。
- 原始排列为 `X0,Y0,Z0,X1,Y1,Z1...`，每值为小端 `int16`。
- 三轴分别进行差分、ZigZag 映射和自适应 Rice 编码。
- 每轴自动选择代价最小的 Rice 参数 `k`。
- 如果压缩结果不小于原始块，自动退回 RAW，保证不会因“不适合压缩的数据”反而膨胀。
- 每块和整批都校验解压后原始字节的 CRC32。
- 每块独立，不依赖前一个窗口，因此单块丢失不影响其他窗口解码。

RAM 中只保留一个 3072 字节原始块和一个最大 3072 字节编码块，不再分配整批 160002 字节数组。

### 7.4 V2 命令

V2 仍复用 Zigbee `0x0402` 温度集群承载私有命令。以下长度不包含 3 字节 ZCL 头：

| 命令 | 方向 | 含义 |
| --- | --- | --- |
| `0x92` | 终端→网关 | 批次描述：版本、批次、采样率、总点数、块大小、整批 CRC、60 字节特征 |
| `0x93` | 终端→网关 | 块描述：批次、块序号、点数、编码方式、压缩长度、块 CRC |
| `0x94` | 终端→网关 | 压缩数据分片：批次、块序号、分片序号、最多 72 字节数据 |
| `0x95` | 终端→网关 | 阶段/窗口确认查询 |
| `0x99` | 终端→网关 | 主动查询最新采样配置；载荷为查询原因 |
| `0x0D` | 网关→终端 | ACK/NACK：阶段、批次、块、状态、64 位缺包位图 |
| `0x0C` | 网关→终端 | 返回当前周期与各传感器采样参数 |

单块最多3072字节，即最多43个72字节分片。0.5/1/1.5秒约为13334/26667/40001点，对应27/53/79个窗口；接收端使用79项窗口状态表。

### 7.5 发送和补传流程

```text
终端 0x92 批次描述
  └─ 网关确认批次身份
      └─ 对每个窗口：
          终端 0x93 块描述
          终端连续发送多个 0x94 分片
          终端 0x95 请求窗口检查
          网关 0x0D 返回缺包位图
          终端仅补缺片，直到该窗口 CRC 通过
      └─ 终端请求整批确认
          网关校验整批 CRC并提交 SQLite
          网关返回最终成功 ACK
          终端将 Flash 槽标为可复用
```

发送节拍为 12 ms，同时最多占用 3 个 APS 发送缓冲。V2 关闭逐包 ZCL 默认响应，但保留 APS ACK 和 Zigbee 网络安全。网关是完整性确认的唯一来源，协调器不能替网关确认数据完整。

确认超时为 3 秒，每阶段最多重试 5 次；本地连续 10 秒无法提交则暂停。暂停时数据仍保留在 Flash，60 秒后自动重试。

### 7.6 网关接收保证

- 最多维护 16 个活动 V2 组包槽。
- 拒绝版本错误、长度越界、块身份冲突、非法分片和 CRC 错误。
- 支持重复包、乱序、缺包、迟到 ACK、ACK 丢失以及网关重启后的重新描述。
- 数据库已经存在相同完整批次时，核对采样率、点数、特征和 CRC，匹配后幂等返回完成，不重复插入。
- 参数相同但内容身份冲突时拒绝，避免错误批次覆盖。
- 数据库写入失败时不返回最终完成 ACK。
- 旧版 `0x8B/0x8C` 解析仍保留，便于过渡；新终端使用 `0x92～0x95`，两者不会混解。

真实已有样本测试结果：26667 个 XYZ 点从 160002 字节压缩为 73188 字节，保留 45.7%，共 53 个 Rice 窗口、1042 个数据分片，解压后逐字节一致。实际空口时间仍需在烧录后的真实网络中测量。

## 8. 协调器功能

协调器负责两类桥接：

1. **网关到节点**：解析串口命令，转换为 Zigbee `0x0402` 集群私有命令并发送到指定短地址。
2. **节点到网关**：接收 Zigbee 私有上报，在前面增加节点短地址，再封装为网关串口响应。

当前关键能力：

- 支持扫描、踢出、关闭入网、查询设备信息、网络信息查询、在线监测控制和采样配置。
- 区分旧网络恢复与自动扫描建网，并通过 `0x9A` 和扩展后的 `0x8A/0x98` 向Linux上报来源和结果。
- 通过 `0x8E` 报告命令进入 Zigbee 队列的状态。
- 通过 `0x90` 报告 AF/APS 无线投递确认和事务号。
- 通过 `0x91` 转发上行原始 ZCL 帧头信息，用于调试命令方向、命令 ID 和负载。
- V2 `0x92～0x95` 原样转发，不产生本地业务 ACK。
- 接收网关 `0x0D` 确认并下发给目标终端。
- UART 写入采用循环处理部分写，避免一次 `UART2_write` 未写满导致帧截断。
- V2 发送不依赖协调器为每个数据分片生成 ZCL 默认响应。

## 9. 网关后端功能

## 10. SQLite 数据库

数据库默认位于 `gateway-core/data/gateway.db`。

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `devices` | 设备白名单和设备影子 | MAC、短地址、在线状态、最新值、监测开关、采集状态、最后活跃/完成时间 |
| `temperature_data` | 温度历史 | MAC、温度、时间戳 |
| `magnetic_data` | 磁场历史 | MAC、XYZ、时间戳 |
| `sound_data` | 数字/模拟声级历史 | MAC、source、dB SPL、时间戳 |
| `monitor_config` | 全局监测策略 | 自动周期、轮询周期、各采样率、麦克风窗口 |
| `collection_values` | 同一采集批次的非振动数据 | `(mac,batch_id)`、温度、XYZ、两路声级、时间戳 |
| `vibration_batches` | 振动批次 | MAC、批次、采样率、点数、原始 BLOB、60 字节特征 BLOB、时间戳 |

注意事项：

- `vibration_batches.samples` 的完整长度应为 `sample_count × 3 × sizeof(int16_t)`；26667 点时约 156.3 KiB。
- `features` 是 15 个 `int32`，共 60 字节。
- 当前 `timestamp` 是网关写入 SQLite 的时间，不是终端 RTC 的高精度采样开始时间。
- 删除设备使用显式事务并启用外键级联，任何一步失败都会回滚。
- 当前表未对 `(mac,batch_id)` 创建唯一约束，但 V2 接收层在保存前执行精确匹配和幂等判断。后续如增加唯一索引，应先处理已有重复历史数据。

## 11. 前端功能

### 11.1 状态总览

- 展示所有已入库节点、在线状态和周期采集状态。
- 所有节点固定开启周期监测，不提供监测开关和立即采集操作。
- 节点卡片展开时主动刷新最新批次；WebSocket 收到采集完成事件后再次刷新。
- 展开详情分别显示温度、数字麦克风、模拟麦克风、三轴磁场、三轴振动特征。
- 振动特征按 X/Y/Z 三行组织，避免多个轴挤在同一格错位。
- 显示采集批次、最近采样时间、原始数据上传进度、波形和下载入口。
- 页面显示“上传完成”，不会在尚未连接远程服务器时宣称“已保存到服务器”。

### 11.2 节点管理

- 开始/停止扫描。
- 查看待加入节点信息。
- 添加白名单、避免重复添加。
- 修改或恢复节点自定义名称。
- 彻底移除节点。

### 11.3 系统设置

- 配置自动采样周期，开发阶段支持 1 分钟；正式应用可设置更长周期。
- 配置振动采样率、两路麦克风采样率和计算窗口。
- 设置保存到 SQLite 后，等待节点在采集结束或重新连接时主动查询。
- 提供系统/串口设置、串口枚举和测试入口。

### 11.4 已清理的无效显示

原先孤立的“睡眠”指示块没有可靠后端状态来源，已从卡片中移除。当前工作状态统一由终端 `0x8D` 状态上报驱动。

## 13. 合并建议

### 13.1 推荐顺序

1. 先合并共享协议头与自动测试。
2. 合并网关数据库和 V2 接收层。
3. 合并网关 `main.c` 的 UART、API、设备移除和 V2 路由。
4. 合并协调器 V2 透传及 `0x0D` 下行。
5. 合并终端 QSPI、采集、压缩和发送状态机。
6. 最后合并前端，确保 API/WebSocket 字段已经存在。
7. 同时升级协调器、网关和终端后再做实机测试。

### 13.2 高冲突文件

以下文件改动集中，不建议直接整文件覆盖同事分支：

- `gateway-core/src/main.c`
- `gateway-core/src/db_manager.c`
- `gateway-ui/src/App.jsx`
- `STM32_WPAN/App/app_zigbee.c`
- `Application/zcl_genericapp.c`

应按功能块合并，并重点检查：命令 ID 是否重复、端点和集群是否一致、数据库迁移是否保留、线程锁范围、终端 UTIL_SEQ 位号、RTC Timer ID、协调器 UART 缓冲长度和 ZCL 最大载荷。

### 13.3 必须保持一致的文件

网关测试端和终端的以下文件当前 SHA256 一致，合并后也应保持相同：

- `vibration_wire.h`
- `vibration_codec.h`
- `vibration_tx.h`

任何一端单独修改协议字段、CRC、编码位序或状态值，都可能导致“能发包但永远校验失败”。建议协议变更同时提高 `V2_VERSION` 并补充测试向量。

### 13.4 升级顺序

推荐实际部署顺序：

1. 停止自动采集；
2. 升级协调器；
3. 升级 Linux 网关和前端；
4. 升级终端；
5. 先做单节点手动采集，再恢复自动监测。

旧协调器不会正确转发 V2，旧网关不会返回 V2 窗口确认。终端在未收到最终确认时会保留 Flash 并重试，因此不能只看 APS 投递成功就认定上传完成。

## 15. 当前测试结论

已通过的软件验证：

- V2 协议和编解码测试；
- 1～512 点所有块长度、常量、斜坡、噪声、极值和随机截断输入；
- 26667 点真实样本无损往返；
- 丢片、重复、乱序、ACK 丢失、永久无 ACK、CRC 损坏和身份冲突；
- Flash 多槽、断电恢复、提交中断、满槽不覆盖、确认释放、移除和旧版迁移；
- SQLite 特征先到/完整批次、失败回滚、幂等、身份冲突和级联删除；
- 实际网关适配层的 UART 前缀、路由、SQLite 保存和重启后重复确认；
- 前端生产构建与静态检查；
- STM32 终端固件完整链接。

## 16. 已知限制和后续实机事项

1. **尚未完成三块真实硬件的最终射频联调**：软件测试和成功编译不等同于真实 Zigbee 网络吞吐验证。
2. **实际上传时间需实测**：现有模拟时间不包含真实射频竞争、终端父节点轮询、UART 调度和 Flash 耗时。
3. **业务配置由网关持久化**：终端重启后依赖重连事件重新下发。如果协调器网络恢复但没有产生网关可识别的入网/上线通知，需要在实机验收中确认配置重放路径。
4. **采样时间语义**：数据库时间是网关入库时间，尚未加入终端 RTC 采样起始时间。
5. **批次显示序号**：前端显示完整批次 ID 的低 16 位，断电后可能重新从 1 显示；完整 32 位 ID 仍用于数据关联。
6. **主频算法**：当前是过零估计，不是 FFT。若后续需要频谱主峰和频域诊断，应单独设计算法、算力和特征协议版本。
7. **模拟麦克风校准**：当前仍是临时参考，工程投产前需要用标准声源完成标定。
8. **Flash 积压能力有限**：测试周期为 1 分钟时可能产生积压；正式 30 分钟以上周期压力较小，但仍应验证最差信道下的上传速率与槽数量。
9. **Zigbee 载荷预算依赖拓扑**：当前最多 79 字节业务载荷基于直连、当前安全和 ZCL 头配置。引入源路由或额外安全头后必须重新核算。
10. **开发阶段串口热切换有限制**：RK3506 部署默认 `/dev/ttyS2`，网页更换串口后建议重启后端。

- [ ] 彻底移除后数据库所有关联数据消失，终端不自动重新入网。
- [ ] 终端 RESET 后可重新扫描加入，且不会上传移除前已作废的数据。
- [ ] 前端展开卡片和采集完成后数据自动刷新，上传状态不会倒退。
