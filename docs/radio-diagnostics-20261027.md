# MAC取包与上传回复诊断

2026-11-03更新：上传回复失败现已在普通模式保留中文类型、编号、批次和窗口，不再依赖详细无线诊断开关。成功结果、MAC观察和轮询仍为可选输出。部署和编号表见 [上传回复类型日志](upload-reply-logs-20261103.md)。以下原始说明中的“关闭诊断”仅关闭详细观察，不再关闭上传回复失败日志。

本次在TI协调器应用层和后端增加可关闭的被动观察，不改变节点轮询频率、MAC间接队列、休眠方式、发送选项、重试和上传排队策略。节点继续使用现有固件。

## 使用

1. 更新TI协调器 `zc_cc1352R_coord` 固件。交付文件位于 `out/radio-diag-20261027/`。
2. 在虚拟机停止旧后端，重新构建共享目录的源码，然后开启诊断并保存完整终端日志：

```sh
cd /mnt/hgfs/Zigbee-Gateway/gateway-core
make -B CC=gcc
ZIGBEE_CONFIG_DIAG=1 ZIGBEE_RADIO_DIAG=1 ./gateway-server 2>&1 | tee "../out/zigbee-radio-$(date +%Y%m%d-%H%M%S).log"
```

确认出现 `被动无线观察已启用`。只有后端的“已请求开启”而没有协调器能力回报，不能认为观察器已经安装；应检查是否更新了协调器、串口是否可用。完整日志保存在共享工程的out目录，以时间命名，可从Windows直接读取。

不设置 `ZIGBEE_RADIO_DIAG=1` 重启后端即可关闭详细观察。后端在串口启动和收到网络信息后发送0x15控制帧，支持协调器重启后重新开启。重复能力回报在后端合并，协调器重启或能力变化会重新显示。

交付的 `gateway-server-linux-x86_64` 仅供x86_64 Linux虚拟机使用；RK3506应从当前源码交叉编译，不能使用这个二进制。前端源码增加了日志事件中文名称，开发模式刷新即可；失败日志正文不依赖前端更新也可显示。

## 看什么

- `上传回复提交`：包含短地址、批次、窗口、回复类型/结果、AF事务号、ZCL序号和提交状态。提交成功只表示接受请求，不能证明已发射。
- `上传回复AF发送结果`：使用提交时保存的元数据及真实AF事务号关联结果，含耗时。AF事务号与ZCL序号分别显示，不混用。事务号255也是有效值。
- `MAC发送最终结果`：被动观察MAC数据确认，记录目的短地址、MAC句柄、直接/间接发送选项、最终状态和重试次数。只有MAC成功且请求了MAC确认时，才显示“MAC ACK已确认”及有效ACK RSSI。它不是逐次发射开始事件。
- `收到MAC取包事件`：只在SDK实际上报 `MAC_MLME_POLL_IND` 时记录短地址、noRsp和累计观测次数。noRsp=1按SDK定义表示该请求以pending位清零的ACK回应，不需要额外MAC发送请求；noRsp=0本身不能证明某条应用回复已经交付。
- `无线观察缓冲溢出`：回调复制队列已满，明确记录丢失数量；原协议栈事件仍继续处理。

提交、成功结果和轮询等高频内容只打印终端。失败、观察能力和诊断丢失写入原有日志数据库，可在前端日志页查看，不因每250ms轮询持续写数据库。

状态明确区分：0xF0=MAC间接事务过期或被清理；0xE9=MAC未收到确认；0xE1=MAC信道接入失败；TI的0xB7=APS未收到确认。原“阶段=APS确认”更名为“AF发送结果（可能包含MAC错误）”，包括兼容旧协调器的0x9F v1失败记录。

## 观察边界

当前TI配置 `macCfg.appPendingQueue` 默认为false。SDK注释说明该选项控制“MAC没有待发送帧时”的应用轮询指示及应用挂起队列处理。本次没有开启或修改该选项，也没有替换网络层的队列管理。因此**轮询事件上报不完整：没有日志、计数为0，都不能证明没有收到取包请求**。缓存计数按短地址累计，可因地址缓存替换而重新计数，不是某个AF事务的精确轮询次数。

观察 `pZMac_AppCallback` 提供的MAC最终结果。MAC句柄与AF事务号属于不同层，当前没有可靠的公开逐帧映射，因此明确按短地址与时间辅助对照，不虚构精确关联。一条“间接发送、MAC成功、MAC ACK已确认”的记录可证明该MAC投递成功；不能据此指定它就是同时在途的哪条AF回复。

“MAC选项=未设间接标志”只描述这次MAC请求的发送选项，不能证明该消息之前没有在NWK等上层队列暂存。

对于失败帧是否曾实际发射、某次MAC轮询是否在空口出现、MAC ACK和APS ACK逐帧时间，需要空口抓包或更底层的完整事件支持。本次不将最终失败结果冒充为发射事件。

## 实现与验证

协调器 `Application/gateway_radio_diag.h` 链接既有观察回调，原样保留前任回调的返回值；不消费、释放、修改原消息，不发MAC请求。回调只复制固定大小的元数据到64槽环形缓冲，不写串口、不打印、不访问SQLite，不保留协议栈内存指针。串口输出由应用任务限量处理，缓冲满仅丢诊断并计数。

UART命令0x15负载为1字节0/1；诊断使用既有0x9F的新版本2，长度40字节，保持版本1的24字节解析兼容。字段：版本/事件[0..1]、协调器毫秒[2..5]、短地址[6..7]、AF事务/ZCL序号[8..9]、回复类型/结果[10..11]、批次[12..15]、窗口索引[16..17]、协议栈状态/标志[18..19]、耗时[20..23]、累计观测轮询[24..27]、最近观测间隔[28..31]、MAC发送选项[32..33]、MAC句柄/重试/有效ACK RSSI/noRsp[34..37]、保留[38..39]。该协议只传输诊断元数据，不传密钥、传感器原始数据或完整MAC帧。

`tests/run-radio-diag-tests.ps1` 测试真实观察器、真实sendZcl和后端处理函数，覆盖回调链/所有权、元数据复制、MAC/APS状态区分、AF255与ZCL255、环形缓冲溢出、关闭观察、能力握手及重启合并、失败入日志、高频事件不入库和畸形数据拒绝。现有可靠控制/上传恢复、配置诊断以及前端日志测试通过；配置诊断测试桩补齐了此前已存在的真实配置打包辅助函数依赖。TI协调器及Linux x86_64完整后端构建通过。
