# 按节点保存上传耗时并估计排队等待时间

网关按设备MAC地址分别学习上传耗时，保存到原有SQLite数据库的新表`upload_timing`。节点仍在采集完成后申请上传，由网关在申请回复中返回许可或等待时间；不提前下发下一采集周期的睡眠安排。

## 统计与估时

- 从取得上传名额开始计时，到波形及特征入库完成、释放名额为止。采集和排队休眠时间不计入本次耗时；占用名额期间的标量校验、等待、补传包含在内。
- 原始波形上传按每个窗口的平均耗时统计，仅特征批次按整批平均耗时统计；两种模式分别保存，互不影响。
- 每条记录保存平滑平均耗时、成功样本数、最近批次ID、最近耗时、最近窗口数及更新时间。
- 第一份成功样本作为初值，后续按旧估计75%、新样本25%平滑更新。原始波形样本先按窗口数归一化，用于不同采集窗口大小的批次。每单位样本限制在500～300000毫秒，最近批次实际耗时仍完整保存。
- 估计某个排队批次时，读取该MAC与上传模式对应的记录：波形平均窗口耗时乘本批窗口数，仅特征使用平均整批耗时，再加5秒余量。
- 暂无历史时，波形使用每窗口3秒加5秒的默认值，仅特征使用10秒。数据库读取失败时同样使用默认值并记录告警。
- 已在上传的节点仍根据本次已校验窗口和实际进度修正预计结束时间。等待者的估计由当前上传者的剩余时间、前面各批次各自的估计耗时及原有交接等待组成。

只有正常完成的上传学习耗时。超时、协议拒绝、撤销、删除及完成记录重确认不学习；重复特征摘要不重复计数。原始波形必须在本次传输中实际接收并校验窗口，不能把数据库中已有波形的快速重确认当作一次很快的新上传。

当前节点的增强批次申请已经携带原始波形是否需要上传的标志，本次直接使用该标志，不改变无线协议。无该能力的旧批次申请按原始波形保守估计。

## 重启及排队规则

耗时统计保存在SQLite中，重启后按MAC读取使用。队列、当前上传者、许可、单调时钟时间戳仍只在内存中，不持久化；重启后由节点重新申请，继续保留原有35秒启动保护。

先申请先排队、队首优先、预计等待时间加30秒的排队有效期、60秒无上传活动超时、25秒节点许可及续期规则不变。预计等待时间不是上传许可。删除节点时通过外键级联删除其耗时统计，其他节点不受影响。

## 日志与更新

每份成功样本保存后，后端终端及前端日志中出现`上传耗时统计`/`upload_timing_saved`，包含MAC、批次、上传模式、本次耗时、平均单位耗时和成功样本数。保存失败记录告警，不影响原批次数据、完成确认和名额释放。

停止旧后端，在虚拟机中执行：

```sh
cd /mnt/hgfs/Zigbee-Gateway/gateway-core
make CC=gcc
ZIGBEE_CONFIG_DIAG=1 ./gateway-server
```

无需重新烧录节点或协调器，也无需更新前端。板端使用原RK3506交叉编译发布流程；检查包中的`gateway-server-linux-x86_64`仅供Linux虚拟机使用。
