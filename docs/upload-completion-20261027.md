# 已完成批次的重确认（2026-10-27）

本次处理“后端已经完整保存批次、释放名额，但节点未收到最终确认，随后续期被拒并重连重传”的收尾问题。MQTT 的 JSON/Sparkplug 发送结果不参与 Zigbee 完成判定。

## 行为

- 新节点重新申请某一批次，后端先查询数据库；如果该批确实完整，直接重放完成回复，不申请名额、不排队、不创建新的 MQTT 上传任务。
- 新节点为已完成批次续期时，同样重放完成回复，不再返回普通的“续期被拒”。回复丢失后可重复请求。
- 其他节点持有上传名额时也能回复旧批完成，不延长、释放或抢占其他批次的名额。
- 节点仅在当前批次身份、传感器校验信息及请求编号匹配时接受回复。回调只停止上传并标记完成；Flash 确认、槽位复用在任务中进行。
- 收尾在上传恢复判断前处理，仍遵守采集、Flash 持久化及无线独占的保护。迟到的上一轮无线失败回调不会把完成批次重新拉入恢复。

## 数据库依据

新增 `upload_batch_receipts` 表，记录 MAC、批次、波形身份、是否要求原始波形和经过验证的配套数据清单。后端启动自动建表。

每次重确认都检查实际数据库记录，不能只看缓存或“已上传”标记：

1. MAC、批次、采样率、点数与保存的身份一致。
2. 如果本批要求原始波形，必须存在完整 XYZ 字节，字节数和 CRC32 一致。
3. 振动特征15项均已保存，不是等待计算的占位值。
4. 清单声明“已采到”的温度、磁场和声级必须存在且校验一致；已声明的采集缺项仍按原规则跳过。

上述依据持久化，后端重启后仍可重确认。记录随节点/原始批次删除而清理；数据已经按保留策略清理时，不会凭空确认。升级前没有保存该清单的旧批次不会直接推定完成，需要原有校验路径补齐依据。

## 协议

协调器继续透传 `0x92`、`0x95` 和 `0x0D`，不需要更新固件。

- 新节点 BATCH 在原77字节后增加能力版本 `1` 和 `raw_required`，总79字节。
- 新节点续期在原10字节后增加能力版本 `1`，总11字节。
- 完成回复仍是17字节 `0x0D`：版本2、kind8、批次、block0、OK；bytes9～12为续期nonce（BATCH重试为0），bytes13～16为身份指纹。
- 身份指纹绑定描述符前17字节、24字节配套数据清单和原始波形策略。特征字不参与身份指纹，因为Flash中的特征会由占位值变成计算结果。
- 旧节点77字节BATCH/10字节续期保持原流程；新回复仅对声明能力的请求发送。**新节点需要新版后端，请先更新后端再烧录节点。**

## 更新与观察

本次只修改网关后端和 `STM32WB55RGV6-BLE-Zigbee` 双模节点工程。前端、协调器无需更新。

虚拟机停止旧后端后：

```sh
cd /mnt/hgfs/Zigbee-Gateway/gateway-core
make CC=gcc
ZIGBEE_CONFIG_DIAG=1 ./gateway-server
```

随后在 STM32CubeIDE 编译并烧录双模节点工程。启动版本标识：

```text
ble-zigbee-upload-completion-20261027
```

最终确认丢失后的预期日志：

```text
[批次完成重确认] MAC=... | 批次=... | 续期/重新申请 | 数据库完整校验通过，无需重新排队或上传
ZIGBEE: gateway confirms batch=... already complete; releasing retained Flash record
ZIGBEE: batch=... raw/features confirmed; Flash record released
```

不要求每个正常批次都出现这些日志；正常最终确认直接到达时仍按原有路径完成。
