# 节点上传通信失败计数调整（2026-11-04）

本次只修改 BLE + Zigbee 节点工程，网关与协调器协议不变。

## 连续失败的范围

只有已提交请求的当前上传代次回调，返回以下结果时才加一次：

| 结果 | SDK 状态 | 处理 |
| --- | --- | --- |
| 未收到 MAC 接收确认 | `0xE9` | 连续通信失败加一 |
| 未收到 APS 确认 | `0xA7` | 连续通信失败加一 |
| 发送确认成功 | `0x00` | 清零连续通信失败计数 |
| 信道接入失败、资源不足、队列满、路由、安全或参数等其他错误 | 其他状态 | 保留诊断，不增加也不清零该计数 |
| 发送接口同步拒绝请求 | 任意非成功状态 | 没有证明发生对端交互，不增加也不清零 |
| 旧上传代次的迟到回调 | 任意状态 | 不影响当前计数 |

累计到四次后仍按原流程暂停上传、保留 Flash 批次、验证协调器通信，必要时恢复原网络。内部错误中间出现时保持计数；一次当前代次的发送成功使计数归零。已触发的验证状态保持原来的锁存行为。

普通振动分片只要求 MAC 确认，控制包还要求 APS 确认。该计数不是窗口校验失败次数，也不是总发送错误统计。状态白名单由节点 SDK 的枚举值通过编译期断言核对。

## 防止绕过计数

此前上传任务还会因为标量重试用尽、特征重试用尽、许可丢失，以及整批曾经出现过任意发送错误/应用回复超时，直接进入网络验证。这些情况可能是本地队列、Flash、编码、后端处理、明确拒绝或应用回复问题，不能单独当作无线失联证据。

现在这些条件仍会停止当前批次、保留待传 Flash 数据并报告上传失败，但不会直接设置通信验证标志。连续四次缺失 MAC/APS 确认仍然触发验证；协议栈已经报告断网时的原有恢复流程也保留。

上传许可仍严格到期停止发送。本次没有延长许可、取消重试或改变排队规则。应用层长时间无回复、但无线发送一直成功时，可能先结束本批尝试并留待后续重试，不再仅凭这一点重建网络。

## 日志

发送失败日志附加：

```
peer_ack_failure=1 consecutive=3 reason=未收到MAC接收确认
peer_ack_failure=0 consecutive=3 reason=不计入通信失败
```

`late=1` 的旧回调永不计数。累计总错误诊断字段仍保留，不能与 `consecutive` 混为一谈。
