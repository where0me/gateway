# 上传回复类型日志

普通运行模式下，上传回复提交失败、发送失败均携带中文类型、类型编号、批次、窗口（适用时）、AF事务号、ZCL序号、中文状态和耗时。失败仍写入原有日志数据库，可在前端日志页面查看。不开启详细无线诊断也能看到这些信息。

| 类型编号 | 中文类型 | 说明 |
| --- | --- | --- |
| 1 | 批次许可 | 批次申请的接受、排队或拒绝结果 |
| 2 | 窗口描述确认 | 窗口描述的接受及发送许可 |
| 3 | 窗口校验结果 | 窗口通过、缺片补传或重新提交等结果 |
| 4 | 整批波形确认 | 整批波形的处理结果 |
| 5 | 振动特征确认 | 特征处理结果 |
| 6 | 传感器数据校验 | 温度、磁场和声级的校验及补传要求 |
| 7 | 上传许可续期 | 当前上传许可的续期结果 |
| 8 | 批次已完成 | 数据库已有完整批次，通知节点释放对应缓存 |

窗口编号对用户从1开始显示；只有类型2、3显示窗口，其余显示“-”。未知类型保留原编号，不猜测语义。

示例（仅展示关键字段，非实测结果）：

```text
上传回复AF发送结果失败 | 短地址=0x487E | 批次=3332029996 | 窗口=12 | 类型=窗口校验结果（编号3）| 回复=缺片补传（0x01）| AF事务=90 | ZCL序号=77 | 状态=MAC间接事务过期或被清理；不能据此判定是否收到轮询（0xF0）| 耗时=190 ms
```

类型编号说明“这是哪一种回复”，状态说明“这条回复的发送是否成功”，回复字段说明“准备告知节点的业务结果”；三者不能混用。AF事务号不是MAC句柄，类型编号也不是事务号。

## 更新与运行

需要同时更新后端与TI协调器，STM32双模节点固件无需更新。协调器新固件在普通模式就会上报带元数据的失败结果；成功、高频轮询等仍只在详细无线诊断模式输出。本次不改变上传回复内容、许可、重试、休眠、信道和安全计数保存行为。

TI固件：`out/upload-reply-log-20261103/zc_cc1352R_coord.hex`。

虚拟机停止旧后端后执行：

```sh
cd /mnt/hgfs/Zigbee-Gateway/gateway-core
make CC=gcc
ZIGBEE_CONFIG_DIAG=1 ./gateway-server
```

保留可选的 `ZIGBEE_RADIO_DIAG=1`，用于查看所有回复提交/结果及被动MAC观察。普通失败日志不需要它。

兼容旧协调器的简略诊断时，后端改称“上传回复失败”，并标注缺失的批次/窗口/类型为“旧版诊断未提供”；不会把未知回复当成窗口校验回复。仅更新后端无法补出旧协调器未发送的信息。
