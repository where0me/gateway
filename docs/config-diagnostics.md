# 采样配置收发诊断

只观察现有通信路径，不改变采样、轮询、重试、休眠、上传队列或配置载荷。默认关闭，不需要重新烧录节点或协调器；需要重新编译后端。

## Ubuntu 虚拟机中运行

先在旧后端窗口按 Ctrl+C 停止旧进程，再在新的终端执行：

```sh
cd /mnt/hgfs/Zigbee-Gateway/gateway-core
make -B CC=gcc
ZIGBEE_CONFIG_DIAG=1 ./gateway-server
```

若当前终端加载过 ARM 交叉编译环境，使用未加载该环境的新终端进行本机开发编译。不要把这个 x86 后端复制到 RK 板；RK 发布包仍使用原有交叉编译流程。

要保存日志，在 Bash 中执行（日志写到 Linux 本地目录，不覆盖以前的文件）：

```sh
set -o pipefail
diag_log=$(mktemp /tmp/zigbee-config-diag.XXXXXX.log)
echo "日志文件：$diag_log"
ZIGBEE_CONFIG_DIAG=1 ./gateway-server 2>&1 | tee "$diag_log"
```

看到 `[配置诊断 ...] 已开启` 才表示新版本和开关已经生效。诊断行带本地日期、毫秒和后端启动后经过的单调时间；它与节点日志中的 `+Xs`、协调器运行时间的起点不同，不能直接相减。诊断行每次立即刷新，重定向时不必等待 stdout 缓冲区满。

停用：Ctrl+C 后直接执行 `./gateway-server`。只有值 `1` 启用；这个前缀只影响本次进程，不会永久修改配置。

## 观察四个阶段

| 标记 | 证明的事情 | 不证明的事情 |
| --- | --- | --- |
| `RX99` | 节点查询已经由协调器转发至后端；原因 `01` 为入网/恢复、`02` 为上传后、`03` 为待机查询 | 只打印节点自己的“query started”不代表查询已到达这里 |
| `TX0C` | 后端准备调用原有串口发送接口，记录实际载荷中的周期、采样窗口、开关和传感器掩码 | 原发送接口返回 void；这条意图日志不能证明串口完整写入，更不证明无线投递 |
| `SUBMIT8E` | 协调器返回的协议栈发送请求提交结果，成功和失败都打印 | 提交成功不等于无线投递完成 |
| `CONFIRM90` | 协调器返回的 AF Data Confirm，成功和失败都打印 | 成功不代表节点已经应用配置；`0xF0` 是 MAC 事务过期，不能直接当作 APS ACK 超时 |

`DROP99` 表示已有的后端过滤条件拦截了查询：未找到已登记 MAC，或节点处于待移除处理。`RX异常` 表示对应串口载荷不足，不会为诊断而修正或回复畸形报文。

这几条日志不是新增协议，不生成确认、不重发配置。原有错误日志仍保留。高频诊断只写终端，不写日志数据库，不打印密钥、MQTT 密码或原始报文。

## 配对限制

当前 TI 桥接的 `0x90` 最后一个字节来自 ZCL sequence；原普通日志把它称为“事务号”。诊断明确写成 `ZCL序号`。`0x99` 和 `0x8E` 没有携带可与它精确配对的请求编号，因此不能把某条确认强行匹配到“最近一次查询”，也不能据此计算精确的单次往返耗时。序号还会回绕，确认可能乱序。

MAC 按打印时的短地址映射解析；未知映射明确标记。短地址变化前后的记录要分段分析，不能把短地址复用误认为同一节点。

## 这次复测

先保留 9D2C 和 1E59，不增加第三个节点。保留异常节点现有串口日志，启动诊断后观察约 30～60 秒：

- 节点打印查询但无 `RX99`：检查上行发送、协调器接收/转发；尚不能仅凭这一点区分具体一层。
- 有 `RX99`，随后有 `DROP99`：先检查本地登记/待移除状态，不归咎于无线下行。
- 有 `TX0C`，没有 `SUBMIT8E`：检查串口写入、协调器接收和桥接处理。
- `SUBMIT8E` 成功，`CONFIRM90` 失败：定位到提交后的无线投递；保留原始错误码。
- `CONFIRM90` 成功但节点仍没有 `sampling configuration accepted`：继续检查节点接收处理；注意并发报文无法精确一一配对。

保存故障前后连续记录，不要只复制带叉号的几行。诊断本身需要重启后端，因此先前内存状态、时间起点会改变；不要同时重启节点或协调器、删除网络或改变接收模式。
