# 节点详情按本轮采集显示（2026-10-27）

本次显示规则取代之前“采集、排队时继续显示最近完整批次”的规则。

| 阶段 | 卡片内容 | 下载和在线波形 |
|---|---|---|
| 尚未开始新一轮采集 | 可显示已有最近数据 | 有完整波形和特征时可用 |
| 开始采集 | 温度、磁场、麦克风、振动特征清空为 `--`，隐藏上批时间 | 禁用 |
| 采集完成、排队或等待醒来上传 | 显示“等待数据上传”，测量区保持空白 | 禁用 |
| 本批开始上传 | 已收到的项目立即显示，尚未收到的保持 `--`；按窗口更新进度 | 禁用 |
| 原始波形已入库、特征未到 | 显示已收到的本批数据及“等待振动特征” | 禁用 |
| 本批波形和特征都完整 | 显示本批结果和时间 | 开放，按 MAC + 批次精确加载 |

温度等实时消息逐项更新；第一个窗口进度、上传状态和完成通知会立即按明确批次刷新详情，不必等到下一次定时器。三秒补查仍保留，处理推送丢失、浏览器重连等情况。早先发起的 HTTP 响应不能把实时新状态覆盖回旧数据。

若上一批仍在上传，同时采集了下一批，先保持正在上传批次的显示；上一批结束后，切换为空白的下一批等待状态。不会把下一批的采集状态与上一批的传感器结果拼在一起。

后端为设备保存当前状态对应批次、最近采集批次及该采集是否仍待完成，页面刷新后也能恢复相同流程。旧数据库在启动时自动增加字段，历史采集记录保留。批次 ID 只比较是否相同，不按数值大小判断先后，支持节点重启后批次 ID 变小。

后端原有 WebSocket 单消息缓冲改为 64 条事件的有界 FIFO。温度、磁场、数字麦克风、超声麦克风在一次网络轮询内连续上报时，各自通知会按顺序发送，避免后发的通知覆盖先发的通知。极端队列溢出仍由定时 HTTP 补查恢复；积压过多的慢客户端会断开并重连，避免其无限占用网关内存。

## 启用

需要重新启动更新后的后端，以启用批次标识和推送队列。虚拟机中停止旧程序后执行：

```sh
cd /mnt/hgfs/Zigbee-Gateway/gateway-core
make -B CC=gcc
ZIGBEE_CONFIG_DIAG=1 ./gateway-server
```

前端开发服务运行时刷新浏览器即可；使用打包页面时需重新部署构建产物。无需重新烧录节点或协调器。

## 验证

- 前端状态测试：开始采集清空、排队、部分实时数据、0/null、旧响应、指定批次、原始波形/特征分步完成、重启批次变小及交叉采集。
- 实际 App 回调测试：迟到的设备列表、立即按批次刷新、漏掉完成通知后的定时补查、多节点隔离及卸载。
- 卡片渲染与波形加载测试：旧测量值和旧时间不再显示，按钮仅在完整后开放，下载仍绑定指定批次。
- 后端真实数据库/API 测试：状态批次和采集批次独立，旧批完成不取消新批等待，字段迁移和既有数据读取。
- 实际 WebSocket 广播函数测试：同一轮询内四条传感器通知、多客户端顺序、缓冲独立复制、有界溢出与慢客户端。
- 传感器校验、原有控制下发和 MQTT 回归，完整 Linux 后端编译及前端生产构建。

本地检查通过，仍需用实际节点验证现场网络下的更新时延。
