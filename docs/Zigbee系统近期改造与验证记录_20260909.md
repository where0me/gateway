# Zigbee 系统近期改造与验证记录

> 日期：2026-09-09  
> 适用工程：STM32WB55 Zigbee 节点、STM32WB55 Zigbee 协调器、Linux 网关后端、React 网关前端  
> 目的：汇总近期围绕信道恢复、低功耗取参、周期采集、设备移除、在线状态和 NVM 清理完成的设计与代码修改，作为烧录、部署和回归测试依据。

## 1. 本轮改造目标

本轮改造的核心目标是把业务发起权从网关转移到低功耗节点，并完善整机断电恢复与设备删除后的行为：

1. 协调器和网关重启后能够恢复或自动建立 Zigbee 网络。
2. 网关不再周期性唤醒节点，也不再主动发起立即采集。
3. 节点在需要采集时主动询问网关，取得最新参数与采集授权。
4. 节点采集可以并行执行，但无线数据必须按固定顺序上传。
5. 睡眠节点被删除后，在下一次唤醒窗口可靠收到离网命令。
6. 节点突然断电时，后端能够在连续错过采集周期后更新离线状态。
7. 节点明确离网或持久化恢复失败时，清除无效 Zigbee NVM。

## 2. 当前系统总体流程

### 2.1 协调器启动

协调器上电后优先检查自身 Zigbee 持久化数据：

```text
存在有效网络记录
→ 恢复原PAN ID、网络密钥和实际信道
→ 向Linux后端上报恢复成功及网络信息

不存在记录或恢复失败
→ 自动扫描11～26信道
→ 自动建立新网络
→ 向Linux后端上报实际PAN ID和信道
```

后端每次启动都会把页面中的“信道策略”恢复为自动选择。恢复出来的实际信道只表示当前网络状态，不会被错误保存为手动目标信道。

### 2.2 节点启动或恢复

节点上电后优先尝试读取自身 NVM：

```text
NVM有效
→ ZbStartupPersist恢复原网络
→ 打开30秒快速接收窗口
→ 发送0x99（原因=1）查询最新配置

NVM不存在
→ 扫描11～26信道
→ 等待协调器Permit Join
→ 入网后打开30秒接收窗口并发送0x99

NVM恢复失败
→ 擦除无效记录
→ 回到普通扫描入网流程
```

节点业务参数不保存在节点 Flash 中，采集周期及传感器参数以网关数据库为准。

### 2.3 正常周期采集

每一轮采集采用以下流程：

```text
采集周期到达
→ 节点打开5秒快速接收窗口
→ 节点发送0x99（原因=2）
→ 后端校验该短地址对应的节点是否仍在白名单
→ 后端用0x0C返回最新采样参数
→ 节点收到并校验0x0C
→ 开始传感器采集
```

如果5秒内没有收到有效 `0x0C`，节点跳过本轮采集，等待下一个完整周期，避免在失去网关授权后继续离线采集和上传。

## 3. 节点主动取参和射频策略

### 3.1 已取消的旧功能

以下旧功能已经从当前业务流程和前端入口中取消：

- 网关主动周期轮询节点；
- 节点每5秒固定打开射频接收参数；
- 单节点在线监测开关；
- 全体在线监测开关；
- 单节点立即采集；
- 全体立即采集。

所有正式入库节点默认开启周期监测，采集由节点 RTC 定时器发起。

### 3.2 当前射频窗口

| 场景 | 接收窗口 | 用途 |
| --- | ---: | --- |
| 首次入网 | 30秒 | 获取初始采样参数和授权 |
| NVM恢复或重新连接 | 30秒 | 获取网关数据库中的最新参数 |
| 每轮采集前 | 5秒 | 发送`0x99`，校验授权并取得`0x0C` |
| 整批上传完成后 | 5秒 | 为采集结束后的必要下行保留窗口 |

等待阶段不再每5秒固定开启射频，从而减少无意义接收和功耗。

## 4. 采集与无线上传顺序

温度、磁场、数字麦克风、模拟麦克风和振动的底层采集可以并行执行，以缩短整轮采集时间。无线发送统一等采集结果准备完成后按固定顺序执行：

```text
0x8D  状态=uploading
0x86  温度
0x87  三轴磁场
0x88  数字麦克风声级
0x89  模拟麦克风声级
0x92  振动批次描述
0x93  振动块描述
0x94  振动数据分片
0x95  振动阶段/缺包查询
0x8D  状态=complete
```

振动批次仍保存在节点外部 QSPI Flash 中。只有后端完成CRC校验并返回最终确认后，节点才释放对应批次并上报完成状态。

## 5. 采样参数保存与下发

在线监测策略保存在网关 SQLite 数据库的 `monitor_config` 表中，不保存在前端页面，也不单独持久化到节点。

前端保存策略时只写数据库，不立即向所有睡眠节点广播。节点在下一次 `0x99` 查询时获得：

- 自动采集周期；
- 振动采样率和采集窗口；
- 数字麦克风采样率和采集窗口；
- 模拟麦克风采样率和采集窗口。

`poll_interval_sec` 仅为旧数据库和旧协议布局兼容保留，不再控制固定5秒射频轮询。

## 6. 删除设备与离网处理

### 6.1 后端和协调器

用户点击“踢出设备”后：

1. 后端先记录设备 MAC 和当前短地址。
2. 后端向协调器发送 `0x02` 离网命令。
3. 后端删除数据库中的设备及相关历史数据。
4. 如果节点当时正在睡眠，后端保留内存中的待移除记录。
5. 节点下一次上行时，后端再次发送离网命令。

协调器的 `0x02` 当前兼容两种载荷：

- 8字节 MAC：用于正常删除和通用重试；
- 2字节短地址：用于在 `0x99` 采集前窗口直接拦截。

节点发送 `0x99` 时，后端如果发现短地址不在白名单并且当前没有开放扫描，将不会返回 `0x0C`，而是立即按短地址发送离网命令。因此删除动作能够发生在传感器采集和批量上传之前。

### 6.2 节点收到明确离网命令

节点收到 `rejoin=0` 的 Leave 后：

```text
停止采集和麦克风
→ 停止振动上传定时器
→ 作废待传振动批次
→ 擦除内部Flash中的Zigbee网络记录
→ 蓝灯熄灭、红灯点亮
→ 设置复位前禁止重新扫描标志
```

离网后协议栈可能再次触发一次持久化通知。当前代码会检查节点是否仍处于已入网状态，防止刚擦除的网络记录被重新写回。

节点明确被踢出后，本次运行不会调用 `UTIL_SEQ_SetTask` 重新扫描。只有按下 RESET 或重新上电后，节点才会以无NVM的新节点状态重新扫描；协调器未开放 Permit Join 时仍无法加入。

### 6.3 网络恢复失败

`ZbStartupPersist()` 最终回调失败说明当前记录已经无法用于恢复。节点会：

```text
打印恢复失败
→ 擦除无效NVM
→ 安排普通Join扫描
```

这与“明确收到踢出命令”不同：恢复失败属于启动异常回退，可以进入普通扫描；主动离网则必须等待复位。

## 7. 突然断电的在线状态

节点突然断电时无法发送 Leave，协调器也不一定立即产生离网事件。当前节点配置中的 `endDeviceTimeout=0xFF` 表示禁用 Zigbee End Device Timeout，因此后端增加了基于业务上行的在线判断。

### 7.1 判定规则

```text
明确收到协调器0x8F离网事件
→ 立即标记离线

没有离网事件
→ 超过“该节点最近实际获得的采集周期×2＋30秒”仍无上行
→ 标记离线
```

例如：

| 节点采集周期 | 自动离线阈值 |
| ---: | ---: |
| 1分钟 | 2分30秒 |
| 10分钟 | 20分30秒 |
| 30分钟 | 60分30秒 |
| 60分钟 | 120分30秒 |

### 7.2 防止修改策略造成误判

数据库为每台节点增加 `expected_interval_sec`，保存该节点最近一次通过 `0x99/0x0C` 实际获得的采集周期。

因此，将全局周期从60分钟修改为1分钟时，尚未醒来的节点仍按原60分钟周期判断，不会在2分30秒后被误判离线。节点下次查询并成功下发新配置后，再切换为新的离线阈值。

有效的 `0x99`、监测状态、温度、磁场、麦克风及振动阶段报文会刷新节点在线活跃时间。为避免大量Flash分片频繁写SQLite，不对每个 `0x94` 数据分片单独写数据库。

后端判定离线后打印：

```text
⚫ [在线超时] 节点 XX:XX:XX:XX:XX:XX:XX:XX 连续错过两轮采集，xxxx 秒无上行，已标记离线。
```

并通过 WebSocket 向前端发送 `status_update`，页面无需刷新即可显示离线。

## 8. 节点公告与短地址更新验证

节点、协调器和数据库正常恢复同一个网络时，短地址通常保持一致，但短地址不是永久设备身份。数据库始终使用64位 MAC 作为设备主标识。

当前链路为：

```text
节点发送Device Announcement
→ 协调器GatewayBridge_AnnounceCallback接收
→ 协调器通过串口发送0x84（MAC＋短地址）
→ 后端按MAC找到原设备
→ 更新数据库中的短地址和在线状态
```

实机恢复日志已经出现：

```text
📥 [底层裸流] 0x84，载荷长度=10
♻️ [静默重连] 已授权设备上线
MAC: 0E:54:EF:00:25:E1:80:00
新短地址: 0x3B91
```

随后同一短地址正常完成 `0x99`、`0x0C`、`0x8D` 和传感器数据传输，证明恢复后的节点公告、协调器转发和数据库短地址更新链路均正常。本轮不再增加重复公告代码。

## 9. Zigbee 信道与网络恢复

### 9.1 后端数据库语义

`zigbee_config` 当前区分：

- `channel_strategy`：页面和当前会话使用的自动/手动策略；
- `target_channel`：手动策略目标信道；
- `actual_pan_id`：协调器实际网络PAN ID；
- `actual_channel`：当前实际信道；
- `startup_source`：旧网络恢复、自动扫描建网或未知来源。

后端重启后把策略重置为 `auto`，但协调器恢复得到的PAN ID和实际信道仍会重新上报并保存。

### 9.2 协调器上报

协调器使用以下报文说明网络状态：

- `0x9A`：无持久化网络、恢复成功或恢复失败；
- `0x98`：网络已经就绪及其启动来源；
- 扩展 `0x8A`：PAN ID、实际信道、设备状态、建网状态、启动来源和最近恢复结果。

实机已验证协调器恢复日志：

```text
✅ [Zigbee网络恢复] 已恢复原网络 | PAN ID: 0x42A2 | 实际信道: 11 | 状态: 0x00
📡 [Zigbee网络] PAN ID: 0x42A2 | 当前信道: 11 | 设备状态: 9 | 建网状态: 0x00
```

## 10. 数据库结构变化

本轮涉及的主要数据库字段如下：

| 表 | 字段 | 用途 |
| --- | --- | --- |
| `devices` | `monitoring_enabled` | 兼容旧结构，当前正式节点统一开启 |
| `devices` | `collection_state` | waiting/capturing/uploading/complete/error |
| `devices` | `last_active` | 最近一次有效上行时间 |
| `devices` | `expected_interval_sec` | 节点最近实际取得的采集周期，用于动态离线判断 |
| `zigbee_config` | `actual_pan_id` | 当前协调器实际PAN ID |
| `zigbee_config` | `actual_channel` | 当前协调器实际信道 |
| `zigbee_config` | `startup_source` | restored/auto_scan/unknown |

旧数据库启动时会自动补充缺失字段。首次增加 `expected_interval_sec` 时，会使用数据库当前全局采集周期初始化已有节点，之后由每台节点的 `0x99` 查询分别更新。

## 14. 建议回归测试

### 14.1 节点恢复

- 关闭扫描后复位已入网节点。
- 确认节点 NVM 恢复成功。
- 确认后端收到 `0x84` 并按 MAC 更新短地址。
- 确认收到原因1的 `0x99` 并成功下发 `0x0C`。

### 14.2 低功耗取参与周期采集

- 修改采集周期，但不主动唤醒节点。
- 等节点原周期到达并发送原因2的 `0x99`。
- 确认节点取得新参数后才采集。
- 屏蔽 `0x0C`，确认5秒超时后跳过本轮。

### 14.3 删除睡眠节点

- 在节点睡眠期间从前端删除。
- 等节点下一次发送 `0x99`。
- 确认后端拒绝下发 `0x0C`并按短地址踢出。
- 确认节点擦除NVM、蓝灯灭、红灯亮，并且复位前不重新扫描。
- 复位节点，确认无旧NVM恢复行为；只有开放扫描后才能重新加入。

### 14.4 突然断电离线

- 设置短采集周期便于测试，例如1分钟。
- 等节点正常上行一次，确认数据库状态为 online。
- 直接断开节点电源，不执行离网。
- 等待2分30秒以上。
- 确认后端打印在线超时日志，数据库和前端均显示 offline。
- 节点重新上电并正常上行后，确认自动恢复 online。

### 14.5 恢复失败

- 使用可控测试方式制造无效持久化记录。
- 确认恢复失败后打印NVM擦除日志。
- 确认不会在每次复位时重复恢复同一份坏记录。
- 开放 Permit Join 后确认节点可以重新加入并保存新网络记录。

## 15. 当前仍需注意的事项

1. 节点基础NVM保存与恢复已经可用，但入网后仍是立即保存。延迟保存、忙碌检查和失败重试属于后续可靠性优化，不是当前功能阻塞项。
2. 恢复后立即收到`0x0C`时，当前节点会立即采集一轮。是否改为“只更新参数并等待完整周期”尚未最终确定。
3. 后端在线超时代码需要在Linux网关执行 `make` 完成目标环境编译，并进行真实断电计时测试。
4. `gateway-core.zip` 是工作区中原有的未跟踪文件，本轮未修改。

## 16. 结论

当前系统已经从“网关主动控制睡眠节点”调整为“节点按周期主动取参和采集”。网络恢复、参数下发、固定顺序上传、睡眠节点删除重试、明确离网NVM清除、恢复失败回退、动态离线判断和短地址更新已经形成完整链路。

下一步重点不是继续扩展协议，而是在Linux网关和实机节点上完成四项回归：采集前取参超时、睡眠节点删除、突然断电离线、无效NVM恢复失败。通过后即可把当前版本作为稳定基线。
