# 重连后恢复采集时点，积压批次可先上传

节点完成网络恢复后，不再因为恢复成功、配置到达、上传结束或普通 REPORT 任务而立即采集。节点先通过状态报文请求网关安排下一次采集，等待过程中仍可申请上传许可并发送 Flash 中未完成的批次。上传许可与采集时点是两个独立机制。

## 时间规则

- 网关按 MAC 读取最近一次已记录的采集开始时间，使用当前保存的采集周期，计算严格晚于当前时间的下一个周期时点。
- 例如最近一次采集为 10:00，周期5分钟，10:03恢复则安排10:05；10:07恢复则安排10:10，不补采10:05。
- 网关没有该节点的采集时间记录时，首次恢复安排在一个完整周期后，并持久化这个临时基准，避免重复请求和后端重启不断后推时间。
- 同一批次的补传和上传完成时间不作为采集基准。此前保存的采集时间是网关收到采集开始通知的时刻，因此这里是基于该观测的周期预测，并非节点与网关之间的精确时钟同步。
- 网关给出目标时间及剩余等待毫秒数；协调器扣除缓存、重试已消耗的等待时间。若已错过时点，顺延至下一周期，禁止立即补采。
- 节点用本地经过休眠仍运行的 RTC 毫秒时基定时。无线在途延迟及计时误差仍会带来偏差，不是硬实时同步方案。
- 同一次恢复的重复配置不重置节点已接受的定时。时间安排无效或未收到时保持等待，继续在有限接收窗口内上报状态，不擅自采集。
- 用户在监测关闭后首次手动开启监测，仍立即开始首次采集；本改动针对网络恢复后的时间安排。

## 协议与状态

三端 `control_sync.h` 一致：A4状态保留8字节，新增 `CONTROL_NEEDS_SCHEDULE` 标志。收到该标志且网关期望监测开启时，即使配置指纹完全相同，后端也必须发送恢复时间。

恢复配置在原29字节采样配置后追加目标Unix秒数、剩余毫秒数，各4字节。普通配置仍为29字节。恢复时间不参与配置指纹，避免每次时间推进都被误判为采样参数改变。

UART同步报文为地址2字节、配置29或37字节、交付模式1字节。协调器使用原有配置窗口/重试机制转发扩展配置，并按实际发送时间调整剩余等待时间。确认状态仍要求匹配配置指纹和监测开关，且节点已清除待安排标志。

节点日志包含：

```text
ZIGBEE: build ble-zigbee-reconnect-cadence-20261103
ZIGBEE: recovery sampling scheduled epoch=... delay=... ms next_rtc=...; cached batches may upload first
```

后端终端与前端日志记录“采集时间恢复”，显示下次采集日期时间、等待时间以及旧批次可先上传。

## 更新与现场验证

这次需要配套更新TI协调器、网关后端、STM32双模节点；前端无需更改。建议先更新协调器与后端，再启动使用新固件的节点。

交付目录：`out/reconnect-sampling-20261103/`。节点 Debug ELF 用于原 STM32CubeIDE 调试下载；Release ELF/HEX 为同一工程优化构建。协调器使用该目录的 `zc_cc1352R_coord.hex`。后端二进制仅适用于Linux x86_64虚拟机，RK3506仍需交叉编译。

虚拟机停止旧后端后：

```sh
cd /mnt/hgfs/Zigbee-Gateway/gateway-core
make CC=gcc
ZIGBEE_CONFIG_DIAG=1 ./gateway-server
```

现有“每次下载固件后逻辑清空外部Flash批次”的规则未改变。验证积压批次恢复，应先烧录本版，再采集并制造断链，不能使用烧录之前的Flash批次验证。

建议观察一次正常采集后、下一周期之前的掉线恢复：网关输出预测时间；节点恢复后先申请旧批次上传，没有新的“节点采集”；到预测的周期后才产生新采集。若恢复已跨过多个周期，应跳过已错过时点。
