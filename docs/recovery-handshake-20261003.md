# 旧网络恢复握手（2026-10-03）

修改范围：纯 Zigbee 节点的 `app_zigbee.c`、协调器的 `gateway_bridge.c`。前端、后端和原 BLE/Zigbee 节点工程不改。

恢复成功后保留当前网络。节点发送公告，并发送携带本轮随机标识和当前短地址的恢复请求。协调器收到公告后发送触发包；收到恢复请求后回送相同随机标识及短地址。所有协调器下行操作由任务处理，不在协议栈回调内嵌套调用 CPU2。

空中私有命令（与同数值的串口命令不是同一协议）：

|命令|方向|载荷|
|---|---|---|
|0x12|协调器→节点|当前短地址，2字节、小端；仅触发请求|
|0x9C|节点→协调器|8字节随机标识+2字节短地址|
|0x11|协调器→节点|原样回送0x9C载荷；恢复确认|

节点只在恢复阶段接受来自协调器短地址0、端点8的确认；长度、随机标识、短地址必须匹配。确认不授予业务授权。重复公告、丢包由请求重试容忍。节点确认后停止恢复定时器，在任务上下文请求后端采样配置；配置、启用状态仍沿用原授权机制。

恢复成功但确认未到时：前两轮间隔10秒，之后间隔60秒，保留凭据并重复公告/握手，不仅因为应用握手超时就执行ZbReset或转新节点入网。真实NVM恢复失败、显式离网等其他路径不被当成握手成功。初始快速轮询以及每轮握手快速轮询用于接收下行。

## 硬件验证

1. 烧录新版节点和协调器CPU1程序，不擦除NVM，不改变CPU2纯Zigbee协议栈。关闭允许加入，启动现有后端。
2. 断电重启已授权节点；观察 `recovery hello queued`、`recovery ACK received`、`restored coordinator verified`、采样配置接受、采集/上传。
3. 节点恢复握手期间不应再出现由验证超时触发的 `admission ZbReset` 或 `fresh 30-second join starts`。
4. 协调器断电/不运行：应出现握手重试日志且保留旧网络；恢复协调器后检查握手和采集能否恢复。
5. 未授权节点恢复：确认不能自动完成授权或启动采集，需人工授权。
6. 实验性注入错误长度、上一轮随机标识或错误短地址的确认，应被拒绝；重复确认不能反复启动采集。

本地静态回归检查和编译不等于硬件空中链路验证。后端未启动时，协调器仍可完成握手，但后端采样配置不能因此凭空产生；配置查询超时行为仍沿用现有实现。
